# 負荷調査と Pi クライアント軽量化の計画

作成 2026-08-06。対象は主機（Ubuntu）側テストモード群と `pi-client/`。

**この計画の前提**: 現時点で実機計測はゼロ。以下の「削れる場所」はすべて処理量からの
見積もりであり、**どれが実際に効くかは未確認**。したがって最適化より先に計測系を作る。

---

## 1. 処理の分類

`pi_client.cc` の1フレーム（192×128 = 24576画素、既定21チャンク）あたりの処理を、
削減方法で3つに分ける。

### A. 消すもの（Pi 側から削除。代替処理を作らない）

| # | 対象 | 現状 | 削減量 | 副作用 |
|---|---|---|---|---|
| A-1 | パレット範囲チェックの全画素走査（[pi_client.cc:325](../pi-client/pi_client.cc)） | 24576回の比較＋分岐を毎フレーム | 走査が丸ごと消える | LUT を 256 エントリへ拡張し余りを黒で埋める。不正値は黒く出るだけ。`dropped` から「範囲外」要因が消える |
| A-2 | `Reset()` の 24KB memset（[pi_client.cc:114](../pi-client/pi_client.cc)） | 毎フレーム 24576 バイトのゼロ書き込み | 24KB/フレームの書き込み | なし。全チャンクが揃わないフレームは表示しないので、ゼロ埋めに意味がない |
| A-3 | 内側ループの `rotate180` 三項演算子（[pi_client.cc:351](../pi-client/pi_client.cc)） | 24576回の分岐×2 | 小（分岐予測が効く） | B-1 を採れば分岐ごと消える |
| A-4 | パケット単位の `clock_gettime`（[pi_client.cc:221](../pi-client/pi_client.cc)） | 60fps で毎秒960回 | 小 | フレーム完成時へ移すだけ。死活報告の粒度は1秒のままなので影響なし |

**消さないもの**（検討して却下）:

- **CRC32**（[pi_client.cc:266](../pi-client/pi_client.cc)）: 60fps でも 1.1MB/s 程度。
  zlib の crc32 なら誤差の範囲で、失う不正フレーム検出のほうが大きい。
- **チャンクの memcpy**: 18KB/フレーム。ゼロコピー化は組み立てロジックが複雑になる割に得が小さい。

### B. 主機に下すもの（Pi の仕事を主機へ移す）

| # | 対象 | Pi 側 | 主機側 | 判定 |
|---|---|---|---|---|
| B-1 | **180度回転** | `dx`/`dy` の座標変換（[pi_client.cc:351](../pi-client/pi_client.cc)）を削除。`--rotate180` も廃止 | 送出前にスライスを反転（`piece[::-1, ::-1]`）。CLI は `--rotate180 0,2` のように target_id を並べる形へ | **採用。** numpy の反転はほぼタダで、Pi 側の per-pixel 計算が完全に消える |
| B-2 | **パレット妥当性の保証** | A-1 と同じ（検査を消す） | 送出前に範囲を保証。`selftest.py` で検証済み | **採用。** A-1 の裏返し。責任の所在を主機へ寄せる |
| B-3 | **送信レートの調整** | なし（Pi は届いた分だけ表示） | Pi の実リフレッシュレートを死活報告から読み、それを超えないレートで送る | **採用。** パネルが追いつかない分を送るのは、受信・CRC・組み立ての純粋な無駄。主機側で絞るのが正しい |
| B-4 | **書き換え範囲の限定（差分更新）** | ヘッダの `dirty_y0`/`dirty_y1` の範囲だけ `SetPixel` | 前フレームと比較して変化した行範囲を算出しヘッダへ載せる | **保留。** 効果は大きいがヘッダー変更を伴う。まず C-1（Pi 側の影バッファ比較）と比較して決める。**計測後に判断** |
| B-5 | **RGB 変換そのもの** | LUT 参照を削除 | RGB 3バイトを送る | **却下。** 帯域が3倍（18KB→55KB/フレーム/台）になり、受信側の負荷が増える |

### C. Pi 側に残すが作り替えるもの

| # | 対象 | 内容 | 判定 |
|---|---|---|---|
| C-1 | **変化画素だけ `SetPixel`** | canvas ごとに影バッファを1枚ずつ（計2枚）持ち、「2フレーム前の自分」と比較して差分だけ書く | **効果は最大の見込みだが、状態が増える。** B-4 と排他。計測で `SetPixel` ループが支配的だと確認できてから入れる |

### D. コード外（設定のみ。コード変更なしで試せる）

| # | 対象 | 内容 |
|---|---|---|
| D-1 | `--led-pwm-bits` | ライブラリ既定 11。`SetPixel` のコストはビットプレーン数にほぼ比例する。FC6 52色 / MSX16 16色は中間調を要求しないので 7〜8 まで落とせる見込み。**最初に試す** |
| D-2 | `--led-slowdown-gpio` | Pi4 では大きすぎるとリフレッシュレートが落ちる。適正値を探る |
| D-3 | `isolcpus` | 描画スレッド用コアの隔離 |
| D-4 | `--led-show-refresh` | パネルの実リフレッシュレートを表示させ、上限が CPU 側かパネル側かを切り分ける |

## 2. 計測しないと判断できないこと

最適化の順番はここで決まる。**先に測る。**

1. **`SwapOnVSync` のブロック時間**が1フレームのどれだけを占めるか。
   ここが支配的なら CPU 側（A-1〜A-4、C-1）の最適化はほぼ無意味で、D-1 が唯一効く。
2. **`SetPixel` ループの実測時間**。C-1 / B-4 に踏み込む価値があるかの判断材料。
3. **受信の取りこぼしがどこで起きているか**。カーネルの受信キュー溢れ（`netstat -su` の
   `receive buffer errors`）なのか、Pi の処理が追いつかないのか。
4. **Pi4 のサーマルスロットリング**の有無。長時間動かすと発熱でクロックが落ち、
   最適化の効果が測定ノイズに埋もれる。

## 3. 作るもの

### 3.1 主機側プロファイラ `host/profiler.py`（新規）

TEST1〜4 で共用する軽量な区間計測。

- `time.perf_counter_ns()` による `with` 文の区間計測
- 区間ごとに 件数 / 平均 / p50 / p95 / 最大 を集計
- **既定は無効**。`--profile` を付けたときだけ有効化し、通常経路のオーバーヘッドをゼロにする
- 終了時に標準エラーへサマリを出す。`--profile-json PATH` で機械可読出力
- 計測区間: `update` / `render` / `quantize` / `slice` / `crc` / `sendto` / `preview` / `sleep`

`UdpFrameSender.send_slices()` の内訳（`tobytes` / `crc32` / `sendto`）も個別に測る。
現状 `send_slices()` は `np.ascontiguousarray().tobytes()` で 4×18KB のコピーを毎フレーム
作っているので、ここが見えるようにする。

**完了条件**: TEST1〜4 のいずれかを `--profile --seconds 10` で動かし、区間ごとの
p50/p95 が数値で出ること。

### 3.2 負荷試験モード `host/test_mode/test5_load.py`（新規）

最適化の効果を測るには、**最良ケースと最悪ケースの両方**を再現できる送信側が要る。

| パターン | 内容 | 何を測るためか |
|---|---|---|
| `static` | 完全な静止画 | 差分更新（C-1 / B-4）の上限性能 |
| `noise` | 毎フレーム全画素ランダム | 差分更新が一切効かない最悪ケース |
| `scroll` | 横スクロール | 中間的な実使用に近い負荷 |
| `solid` | 全画面単色（フレームごとに色を変える） | 伝送と表示だけの下限コスト |

- `--fps` を段階的に上げて破綻点を探す `--ramp 10:120:10`（10fpsから120fpsまで10刻み）
- 各段で Pi 側の実表示fpsと欠損数を死活報告から読み、**送信fpsと表示fpsが乖離し始める点**を記録
- 出力は CSV（`--csv out.csv`）。後から比較できる形で残す

**完了条件**: ローカル（`--pi 127.0.0.1:5000` ×4）で全パターンが動き、CSV が出ること。
実機での ramp 実行は Pi 側（3.3）が入ってから。

### 3.3 Pi 側の区間計測（`pi-client/pi_client.cc` を拡張）

`--profile` 付きのときだけ計測する。区間は `clock_gettime(CLOCK_MONOTONIC)` の差分と
指数移動平均で持つ（配列に貯めない＝動的確保しない方針を維持）。

| 区間 | 測る内容 |
|---|---|
| `recv_wait` | `recvfrom` のブロック時間 |
| `assemble` | CRC32 検証＋memcpy |
| `validate` | パレット範囲走査（A-1 の効果測定用。A-1 を入れたら消える） |
| `convert` | `SetPixel` ループ全体 |
| `swap` | `SwapOnVSync` のブロック時間 ← **最重要** |

加えて、フレーム単位ではなく取れる指標:

- CPU 使用率: `/proc/self/stat` の `utime`+`stime` の差分
- 温度: `/sys/class/thermal/thermal_zone0/temp`
- スロットリング: `vcgencmd get_throttled`（外部プロセス起動になるので**表示ループ外**、
  死活報告のタイミングでのみ。頻度は10秒に1回程度に落とす）
- カーネル受信バッファ溢れ: `/proc/net/snmp` の `Udp: InErrors` / `RcvbufErrors`

**PIHEALTH の拡張**: 現在の形式は `key=value` の空白区切りで、`test2_status.py` は
`fields.get()` で既知キーだけを読む（[test2_status.py:86-97](../host/test_mode/test2_status.py)）。
**キーを追加しても既存の TEST2 は壊れない**ことを確認済み。1行 512 バイト以内に収める。

```text
PIHEALTH target=0 displayed=1234 dropped=2 fps=59.8 up=41 rot=0 \
  recv=1.2 asm=0.8 conv=4.1 swap=9.6 cpu=62 temp=71.2 thr=0 rxerr=0
```

**完了条件**: Pi 実機で `--profile` を付けて起動し、TEST2 の画面に上記の値が出ること。

### 3.4 TEST2 への計測表示追加（`host/test_mode/test2_status.py`）

各 Pi のページに区間内訳を追加する。ページが縦に足りなければ「PROF」ページを分ける。
`swap` が支配的かどうかがひと目で分かる並びにする（`swap` を最上段）。

**完了条件**: 3台ぶんの区間内訳が LED 上で読めること。

## 5. 判断の分岐（S7 の結果次第）

| 測定結果 | 次にやること |
|---|---|
| `swap` が1フレームの大半 | D-1（pwm_bits）と D-2 のみ。CPU 側の最適化（C-1 / B-4）は**やらない** |
| `convert`（SetPixel）が大きい | C-1（影バッファ差分）を実装。効果が足りなければ B-4 へ |
| `recv_wait` 以外が小さく余裕がある | 軽量化より B-3（送信レート調整）で無駄な送信を止めるほうが先 |
| `rxerr` が増える | 受信バッファか NIC 側。`SO_RCVBUF` とカーネルパラメータを見る |
| `thr` が 0 でない | 発熱対策が先。他の測定値がすべて信用できなくなる |

## 6. 注意

- **計測コードは既定で無効**にする。`--profile` なしのときは分岐1本で素通りさせ、
  「計測を入れたら遅くなった」を避ける。
- A-1（LUT 256化）を入れると `validate` 区間が消える。**A-1 の前に一度測っておく**こと。
  効果を数字で示せなくなる。
- 最適化を入れるたびに ramp を回し直し、CSV を残す。**前後比較のない最適化は入れない。**
