## 1. 発端：センサーとバーの同期遅延

「センサーと下のバーが同期が遅い」という報告から着手。

### 原因

センサーPi側で**古い深度フレームを順に処理していた**のが主因。
`StructureSensorSource.read()` はヘルパーのパイプから先頭（＝最古）フレームを読むだけなので、
1周の処理が取得周期（30fps＝33ms）を超えると滞留分がそのまま固定遅延になる。
加えて `sensor_agent`（誰も表示しない経路）が毎フレームデバッグプレビュー（`depth_preview` の
percentile＋カラーマップ＋輪郭描画）を描いており、Pi3でその処理落ちを自分で作っていた。

### 修正（Mac実測・Pi3実機実測とも完了）

| ファイル | 内容 |
|---|---|
| [host/frame_source.py](../host/frame_source.py) | 取得を専用スレッドに分離し、`read()` は未処理の最新フレームだけを返す（滞留分は破棄して `dropped` に計上）。フレーム受信も `readinto` 化してコピー削減 |
| [host/block_breaker.py](../host/block_breaker.py) | `SensorController(debug_preview=…)` 追加。プレビューは見る側だけが描く。`ForegroundGate.detect_all` の行スパン計算をベクトル化（Pythonループ→numpy一括） |
| [host/sensor_agent.py](../host/sensor_agent.py) | `debug_preview=False`。health行に `stale_dropped` / `loop_fps` / `loop_max` を追加（処理落ちが数字で分かる） |
| [host/structure_depth_capture.cpp](../host/structure_depth_capture.cpp) | `--decimate N` 追加（N画素おきに間引いて送出、転送量1/N²）。OpenNI2スタブでビルド・実行検証済み（decimate=1〜4で最近傍間引きと完全一致） |
| [host/frame_source_selftest.py](../host/frame_source_selftest.py) | 新規。滞留フレーム破棄・decimate・ヘルパー異常系のセルフテスト |

**`--capture-decimate`（既定1）は既定でヘルパーへ引数を渡さないため、旧バイナリでも動く。**
ROI指定時は自動無効化（ROIは取得解像度の座標系のため）。

### 実測結果

**Mac（擬似深度、人物往復トラッキング、処理が追いつかない条件）**

| | 推定遅延 |
|---|---|
| 旧 | 100ms |
| 新 | 20ms（≒1フレーム） |

**Pi3実機（実センサー、`read()` 1回あたりCPU時間）**

| | CPU/frame |
|---|---|
| 旧（プレビュー描画あり） | 17.4〜20.9ms |
| 新 decimate=1 | 8.0〜8.8ms |
| 新 decimate=2 | 7.3〜9.5ms |

**実機の `stale_dropped=0 loop_fps=30.0` を確認済み**（新コード稼働中に取得）。

## 2. ゲームロジック：developのブロック崩しを通常面として復活

ユーザー指示「ゲームロジックはdevelopブランチのものを利用」への対応。

### 事実確認

develop（fa8f837）は master から分岐した古い版で、**RGBカメラ＋ブロック崩しのみ**
（深度センサー分離ランタイムが無い＝frame_source.py/input_transport.py/sensor_agent.py/
structure_depth_capture.cpp が存在しない）。develop を丸ごと取り込むと今回のセンサー修正が
消えるため、**developのブロック崩しロジックだけを現行ランタイムへ移植**する方針をユーザーに
確認し、承認を得た（「ブロック崩しを通常面として復活させ、クリア後にボス戦」）。

### 実装

`BlockBreaker` に `phase`（`"classic"` / `"boss"`）を追加。

- 通常面（`classic`）: developの `_make_blocks` / `_hit_block` / `_launch` の係数をそのまま移植
  （8列×6行、加点10×level、developと同じ発射角）
- 全消しで `STAGE CLEAR` を1.8秒表示 → ボス戦（`boss`）へ自動遷移
- ボス戦の1球目は、ミス後と同じ「操作対象を選び直して静止開始を待つ」に揃えた
  （`consume_stage_start_request()` を新設。無いと `still` モードの開始検出がラッチされたまま
  になりボールが永久に発射されない）
- ボス撃破 → 通常面（`classic`、レベル1）へ戻る
- `host/extra_stage_block_breaker.py`（通常面付きキーボード試作）は
  `BlockBreaker(start_phase="boss")` でボス戦だけを使うよう1行修正（試作側は独自の通常面ロジックを保持）

### 検証

- セルフテスト7本 0 errors（[block_breaker_selftest.py](../host/block_breaker_selftest.py) に
  通常面・ステージ遷移・MSX16描画の検証を追加）
- 各場面を実描画してPNGで目視確認（待機・カウントダウン・プレイ中・STAGE CLEAR・ボス待機・ボス戦、
  FC6/MSX16両パレット）
- main()の実行経路で通し運転（単機構成・分離構成の両方）、
  `event=stage-clear next=boss ... wait=still-hold` → 再検出 → カウントダウン → ボス戦発射まで確認

## 4. ネットワーク・運用上の注意点（今回新規で分かったこと）

メモリ（`hackathon2026-pi-access.md`）にも追記済みだが、要点:

- **Macの `192.168.10.50` は手動alias。USB-Ethernet(AX88179A/en9)のリンクが一瞬でも落ちると消える。**
  自動で戻るのは `192.168.20.50` だけ。全機無応答に見えたら `ifconfig en9` の `inet` 行を確認。
  復旧は `sudo ifconfig en9 alias 192.168.10.50 netmask 255.255.255.0`（sudoパスワードが要るため
  エージェントからは実行不可、ユーザー側で実行が必要）
- **センサーPi（192.168.50.33）は公開鍵のみ。** Mac単体では `192.168.50.0/24` への経路が無いため、
  鍵登録後は `ssh -J takemuralab@192.168.10.2 takemuralab@192.168.50.33` の踏み台接続で到達する
  （`192.168.50.0/24` のalias追加は不要）
- センサーPiはRTCが無くNTPにも届かないため時刻がずれる。ビルド前に時刻同期が必要
  （`make`/`g++`がclock skewでリンクを飛ばすことがある）
